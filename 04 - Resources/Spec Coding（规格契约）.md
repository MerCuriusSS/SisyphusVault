### 一、定义

- **外部视角下描述条件‑结果**的系统行为契约，强调**做成什么样**
### 二、价值

- 显式边界，统一验收，约束人与 AI 开发

### 三、Spec 内容组成

- 多条 Given‑When‑Then 场景集合，只写外部观测现象。


### 四、Spec（规格契约）和 RD（需求文档）、DD（详细设计文档）的区分和关系

- RD 需求文档：描述业务意图、故事、范围；**讲故事**
- 详细设计文档：内部实现方案，用什么技术怎么执行；**材料+工序**
- Spec：呈现外部观测视角下的所有条件和执行结果；**做成什么样**

#### **关系：RD → Spec  → DD**

- RD诉求转化为Spec
- Spec实现对与错的判断基准
- DD是实现Spec的手段

```
RD（业务愿望） → 评审 RD
↓
Spec（外部行为契约，由 RD 诉求转化而来） → 评审 Spec（产品可参与评审，不需要懂技术）
↓
DD（内部实现方案，必须完整满足 Spec 全部条款） → 评审 DD，核对是否对齐 Spec
↓
编码开发，对照 Spec 做验收
```

### 五、Spec 的选取粒度

- 默认推荐粒度：独立业务功能点，可向上合并成模块
- 不以内部技术零件（DAO、RPC、MQ）划分
- 划分判断标准：
	- 外部观测者（用户 / 外部服务）可以感知该单元
	- 替换内部实现技术，Spec 文档不需要改动
