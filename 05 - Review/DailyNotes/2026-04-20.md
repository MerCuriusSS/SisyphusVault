### 反转链表（部分）
- 题型（1->2->3->4->5;反转【2,4】区间中的元素）
- 初想法：
	- 直接对原链表修改
		- 获取位置为1的元素指针p1和位置为2的元素指针p2；
		- 反转【2,4】的链表；
		- 记录位置为5的指针p3；
		- p1指向反转后链表的头节点；
		- p2指向p3节点。
- 卡壳点：
	- 分解思维不足，追求一把梭，反转链表的轮子应该适当封装起来
	- 反转链表特点掌握不熟练——每次反转后，cur都会「自动」标记为下个节点。
- 破局点：
	- 反转链表的轮子代码应该抽象封装起来。
	- 掌握反转链表的特征：先指前，再后挪；反转后cur指向下节点\
	- for循环小技巧： 访问对象是「现实问题」 or 「索引」，决定「**i=0/1**」；要走到哪个位置「**i<k**」
- 核心代码；
- ```java
  public ListNode reverseBetweenList(ListNode head,int n,int m){
	  if(n==1){
		  return reverseNList(m);
	  }
	  ListNode pre=head;
	  
	  //获取第n-1个节点的指针
	  for(int i=1;i<m-1;i++){
		  pre=pre.next;
	  }
	  
	  pre.next=reverseNList(pre.next,m-n+1)
	  
	  return head;
  }
  
  public ListNode reverseNList(ListNode head,int n){
	  if(head==null||head.next==null) return head;
	  ListNode pre=null;
	  ListNode cur=head;
	  ListNode nxt=cur.next;
	  while(n>0){
		  //特征1：先指前，再挪后
		  cur.next=pre;
		  pre=cur;
		  cur=nxt;
		  if(nxt!=null){
			  nxt=nxt.next;
		  }
		  
		  n--;
	  }
	  
	  //特征2：cur指向下个指针
	  //先前的head（后面的链表末）指向cur
	  head.next=cur;
	  return pre;
  }
  ```

### 树的三层B+能存多少数据
- 常规情况下能存2000w+数据
	- 页大小为16kb、主键为bigint类型8字节、页指针6字节=>（16✖️1024）➗️14字节≈1170个节点
	- 行数据1kb，一页数据量为16。
	- 三层树结构总数据量为1170`*`1170`*`16≈2190万条数据

B+树存储受几个因素影响：
- 页大小：决定存储空间（蛋糕有多大）
- 主键大小：扇出程度有多大（能切多少份）
- 行数据大小：总存储量有多大


### 回表
- 什么是回表？即查两次表，二级索引查完，再去主键查一遍。
- 性质/特征：
	-  多一次I/O，速度变慢；返回多个不连续的主键触发多次随机I/O，效率降低，直至不如`全表查询
- 为什么需要回表？二级索引只保存索引字段 + 主键，不存整行数据，当查询的字段在二级索引中不满足时，需要会聚簇索引中进行二次查找。
- 怎么做？
	- 先根据二级索引查询主键值
	- 根据主键值从聚簇索引中再查目标内容。
- 怎么用？
	- 覆盖索引，保证`select`的字段、`where`筛选的条件、`排序`的顺序在二级索引中全满足。

### 索引下推（ICP）：
- **是什么**？在引擎层中把二级索引能筛的条件全筛了，再回表查询的优化手段。
- **性质/属性**：`idx(a,b,c) select * from tbl1 where a=1 and b like '梁%'` 
	- 非索引覆盖
	- 联合索引
	- 含索引条件查询
- **为什么**？
	- 引擎层笨，只能根据最左前缀的`某个字段`进行初筛查，其余查询条件留到「回表」后统一查询。初筛查的宽松使回表次数增多，I/O操作多，查询慢。
	- ICP操作使回表次数少，且更符合「联合索引」的`直觉查询`。
- **怎么做**？`引擎层：放数据的地方`、`server层：优化、缓存的地方`
	- 在「引擎层」中将二级索引相关的查询条件都用上，返回筛查后的行数据到「server层」
	- server层中根据行数据再回表拿最终数据。
