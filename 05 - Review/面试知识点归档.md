## 一、Kafka

记录日期：2026-03-24、2026-03-27

### 1. Kafka 定位

Kafka 可以理解为一个大、快、稳、分布式的消息中间件，本质上是业务系统之间的缓冲管道。

核心作用：

- 解耦：上游服务不直接依赖下游服务，只负责发送消息到 Kafka。
- 削峰：承接瞬时高流量，再平滑交给下游消费。
- 异步：发送消息后即可返回，提高用户体验。
- 负载均衡：通过分区和消费组实现生产端、消费端的并行处理。

### 2. 核心组成

- broker：Kafka 消息服务器，负责存储和转发消息。
- producer：消息生产者。
- consumer：消息消费者。
- topic：消息分类，通常按业务划分。
- partition：分区，决定存储并行度和消费并行度。
- consumer group：消费组。
- offset：消费组在某个分区内的消费进度。

### 3. 消费组

消费组是为一批消费者设定一个共同组名，用于统一管理消费进度。

多消费组之间：

- 可以独立消费同一份数据。
- 效果类似广播，每个消费组都可以完整消费一份消息。

单消费组内部：

- 多个消费者共同分摊消费。
- 一个分区在同一个消费组内只能被一个消费者消费。
- 分区数量决定该消费组的最大消费并发数。

面试表达：

> Kafka 的消费组既能支持广播，也能支持负载均衡。不同消费组之间互不影响，同一消费组内多个消费者分摊分区，但一个分区同一时刻只能分配给组内一个消费者，因此 partition 数量决定了消费组最大并发度。

### 4. Offset

offset 是消费组在分区内的消费进度。

唯一标识：

```text
消费组 + 分区
```

作用：

- 记录消费进度。
- 支持失败后继续消费。
- 支持消息回溯。
- 是保证不丢、不重复处理的基础。

提交方式：

- 自动提交：实现简单，但业务未处理成功时可能已经提交 offset，存在丢消息风险。
- 手动提交：业务处理成功后再提交 offset，更安全，但需要处理重复消费和异常场景。

### 5. Rebalance

Rebalance 是消费者或分区发生变化时，Kafka 重新分配分区的过程。

触发时机：

- 消费者加入。
- 消费者离开。
- 消费者宕机。
- 分区数量增加。
- 消费者心跳超时。

关键影响：

- Rebalance 期间消费者会暂停消费。
- 如果频繁 Rebalance，会影响消费稳定性和吞吐。

### 6. 消息丢失场景

生产者端：

- `acks = 0`：生产者发送即认为成功，broker 未写入也不会感知，可能丢消息。
- `acks = 1`：leader 写入后确认，但 follower 尚未同步时 leader 宕机，可能丢消息。

消费者端：

- 自动提交 offset：业务还没处理完，offset 已提交，消费者挂掉后消息不会再消费。
- 手动提交 offset：业务异常被吞掉，但仍手动提交 offset，也会造成丢消息。

后续建议补充：

- 如何保证 Kafka 消息不丢。
- 如何解决重复消费。
- 幂等消费如何设计。
- 如何保证顺序消费。

## 二、MySQL 与 SQL 调优

记录日期：2026-04-01、2026-04-15、2026-04-16、2026-04-20、2026-04-21、2026-04-25、2026-04-27

### 1. 存储引擎

存储引擎是 MySQL 管理数据的方式，决定数据如何存、如何查、如何改，以及如何保证安全。

主要关注维度：

- 数据怎么存：存储文件、外键。
- 数据怎么查：索引结构、B+ 树。
- 数据怎么改：锁、事务、MVCC。
- 风险与安全：崩溃恢复。

InnoDB 与 MyISAM 对比：

| 维度 | InnoDB | MyISAM |
| --- | --- | --- |
| 事务 | 支持 | 不支持 |
| 锁 | 行锁 + 表锁 | 表锁 |
| MVCC | 支持 | 不支持 |
| 外键 | 支持 | 不支持 |
| 索引 | 聚簇索引 | 非聚簇索引 |
| 崩溃恢复 | 通过 redo log、undo log 支持 | 较弱 |
| 场景 | 高并发、频繁增删改、数据安全要求高 | 读多写少、简单业务 |

面试表达：

> InnoDB 更适合现代业务系统，因为它支持事务、行锁、MVCC 和崩溃恢复，能在高并发读写场景下保证数据安全和并发性能。MyISAM 不支持事务和行锁，更适合简单读多写少场景。

### 2. 聚簇索引与非聚簇索引

聚簇索引：

- 叶子节点保存主键列和完整行数据。
- InnoDB 的主键索引就是聚簇索引。
- 通过主键查询可以直接拿到完整数据。

非聚簇索引：

- 叶子节点保存索引列和主键列。
- 查询非索引字段时，需要先通过二级索引找到主键，再通过主键回表查询完整数据。

回表：

- 二级索引查到主键后，再去聚簇索引查完整行数据。
- 多一次 IO。
- 如果返回大量不连续主键，会产生大量随机 IO，性能下降。

优化方式：

- 使用覆盖索引，让 `select` 字段、`where` 条件、排序字段都能从二级索引中满足。

### 3. 索引类型

按数据结构：

- B+ 树索引
- Hash 索引
- 全文索引

按约束类型：

- 主键索引
- 唯一索引
- 普通索引
- 联合索引
- 全文索引

按存储方式：

- 聚簇索引
- 非聚簇索引，也叫二级索引

### 4. 为什么 MySQL 使用 B+ 树作为索引结构

核心原因：

- IO 更少。
- 范围查询更快。
- 查询性能更稳定。

IO 更少：

- 非叶子节点只存索引键和页指针。
- 单页能容纳更多 key。
- 树的扇出更高，高度更低。
- 查询需要的磁盘 IO 次数更少。

范围查询更快：

- 数据集中存放在叶子节点。
- 叶子节点之间通过链表连接。
- 范围查询可以顺序扫描叶子节点。

性能更稳定：

- 所有查询最终都要到达叶子节点。
- 查询路径长度相对稳定。

### 5. 三层 B+ 树能存多少数据

记录中的估算：

- 页大小：16KB。
- bigint 主键：8 字节。
- 页指针：6 字节。
- 非叶子节点一项约 14 字节。
- 一页约可存 `16 * 1024 / 14 ≈ 1170` 个索引项。
- 如果一行数据约 1KB，则叶子页一页约 16 行。
- 三层树可存约 `1170 * 1170 * 16 ≈ 2190 万` 条数据。

影响因素：

- 页大小。
- 主键大小。
- 行数据大小。

面试价值：

> B+ 树为什么三四层就能支撑千万级数据，本质在于非叶子节点只存 key 和指针，扇出非常高，树高很低，所以磁盘 IO 次数少。

### 6. 最左前缀匹配原则

定义：

联合索引的匹配规则是从左到右、连续不跳步。

原因：

- 联合索引底层按字段顺序排序。
- 例如 `(a, b, c)`，先按 `a` 排，`a` 相同再按 `b` 排，`b` 相同再按 `c` 排。
- 跳过前面的字段，后面的字段无法利用有序结构定位。

生效条件：

- 查询条件包含从左往右连续字段。
- 出现范围查询时，后续字段索引通常失效。

使用建议：

- 高频字段靠前。
- 区分度高的字段靠前。
- 范围条件尽量放在联合索引末尾。
- 避免 `select *`。

### 7. 索引下推 ICP

定义：

索引下推是在存储引擎层尽可能使用二级索引中的条件进行过滤，减少回表次数的优化手段。

适用场景：

- 联合索引。
- 非覆盖索引。
- 查询条件中有部分条件可以在索引层判断。

价值：

- 减少回表。
- 减少随机 IO。
- 提升联合索引的过滤效率。

### 8. 索引生效、失效与效果差

索引生效：

- 主键索引快速查找。
- 二级索引快速查找。
- 全扫描二级索引。

索引失效常见原因：

- 索引列使用函数。
- 索引列参与运算。
- 隐式类型转换。
- `like` 左侧带通配符。
- `or` 连接非索引字段。
- 联合索引破坏最左前缀原则。
- 无 `where` 条件并按非索引字段排序。

索引效果差：

- 回表次数太多。
- 索引选择性差。
- 返回数据量过大。
- `Extra` 中出现 `filesort`、`temporary`。

优化优先级：

```text
覆盖索引 -> 联合索引顺序优化 -> limit -> 避免 select * -> 避免 filesort
```

### 9. Explain 观察点

重点字段：

- `type`：访问类型。
- `key`：实际使用的索引。
- `rows`：预估扫描行数。
- `Extra`：额外执行信息。

常见访问类型：

- `ALL`：全表扫描。
- `INDEX`：全索引扫描。
- `RANGE`：范围匹配。
- `REF`：等值匹配。

大致优劣：

```text
ALL < INDEX < RANGE < REF
```

### 10. SQL 调优

调优方向：

命中索引：

- 避免全表扫描。
- 避免索引全扫描。
- 根据高频访问和高区分度设计联合索引。
- 遵循最左前缀原则。
- 避免函数、类型转换、左模糊、逻辑非等写法。

减少回表：

- 使用覆盖索引。
- 查询字段、筛选字段、排序字段尽量由联合索引覆盖。

减少 IO：

- 主键尽量短小，提高 B+ 树扇出。
- 使用 `limit` 控制结果集。
- 分批查询。
- 冷热数据分离。
- 分库分表。
- 分区。
- 调整缓冲池。
- 对固定 join 关系做宽表。

### 11. Count、Char、Varchar

`count(*)`、`count(1)`、`count(字段)`：

- `count(*)` 和 `count(1)` 都统计所有行。
- `count(字段)` 会排除字段值为 `NULL` 的行。
- `count(*)` 会优先选择代价较小的索引。

`char` 与 `varchar`：

- `char` 是定长存储，不足长度时用空格补齐。
- `varchar` 是变长存储，按实际字符长度存储，并额外使用 1-2 字节记录长度。

### 12. MySQL 事务实现

事务依赖：

- RedoLog
- UndoLog
- 锁
- MVCC

RedoLog：

- 保证事务持久性。
- 预写日志。
- 先写日志，后刷数据。
- 用顺序 IO 和异步刷盘减少随机 IO。

UndoLog：

- 保证事务原子性。
- 支持回滚。

锁 + MVCC：

- 保证隔离性。
- 提高并发读写能力。

## 三、Java 集合

记录日期：2026-04-02

### 1. HashMap

定义：

HashMap 是 Java 集合中的一种键值对数据结构，结合数组和链表的优点，在理想情况下可以用 `O(1)` 时间复杂度完成增删改查。

组成：

- Node 数组。
- 哈希函数。
- Node 节点。
- 链表。
- 红黑树。

Node 节点字段：

- key
- value
- next
- hash

执行过程：

1. key 计算 hash 值。
2. 通过 `hash & (cap - 1)` 计算数组下标。
3. 判断是否存在哈希冲突。
4. 无冲突时直接放入数组。
5. 有冲突时挂到链表或红黑树。
6. 元素数量超过阈值后触发扩容。

扩容：

- 当元素数量超过容量与负载因子的乘积后触发。
- 新数组容量为原来的 2 倍。
- 元素重新分布。
- JDK 1.8 中节点要么留在原位置，要么移动到 `原下标 + oldCap`。

扰动函数：

- 将 hashCode 高 16 位与低 16 位异或。
- 让高位也参与下标计算。
- 减少哈希碰撞。

容量为什么是 2 的幂：

- 可以用位运算代替取模。
- 扩容迁移判断更简单。
- 节点位置要么不变，要么原下标加旧容量。

树化阈值 8：

- 正常哈希分布下，单桶冲突达到 8 的概率极低。
- 避免频繁树化。
- 极端场景下用红黑树保证查询性能。

## 四、JUC 并发

记录日期：2026-04-02、2026-04-03、2026-04-08

### 1. ConcurrentHashMap 1.7

实现方式：

- Segment 分段锁。
- Segment 继承 ReentrantLock。
- 每个 Segment 管理一部分桶数组。

特点：

- 同一个 Segment 内串行。
- 不同 Segment 之间可以并行。
- 锁粒度较粗。
- 并发度受 Segment 数限制，默认约 16。

缺点：

- Segment 数固定时，并发上限有限。
- 桶数量增多后，同 Segment 竞争会加剧。
- 内存开销相对更高。

### 2. ConcurrentHashMap 1.8

实现方式：

- Node 数组。
- CAS。
- synchronized 锁桶头。

执行过程：

- 空桶插入使用 CAS。
- 桶内已有节点时，对桶头加 synchronized。
- 不同桶之间可以并行。
- 并发度随桶数组长度增加。

优点：

- 锁粒度更细。
- 并发能力更强。
- 舍弃 Segment，降低内存开销。

### 3. ConcurrentHashMap 1.8 扩容机制

核心组件：

- `sizeCtl`：记录扩容阈值和线程协助扩容状态。
- `stride`：每个线程负责迁移的区间大小。
- `transferIndex`：迁移区间分配下标，从后往前分配。
- `ForwardingNode`：表示当前桶已经迁移完成。

流程：

1. 触发扩容后，`sizeCtl` 变为扩容状态。
2. 首个线程 CAS 创建新数组。
3. 初始化 `transferIndex`。
4. 多个线程按 `stride` 领取迁移区间。
5. 空桶放置 `ForwardingNode`。
6. 已迁移桶跳过。
7. 普通桶加 synchronized 后迁移到新表。
8. 迁移完成后修改 `sizeCtl`。
9. 最后一个线程替换 table，并设置新阈值。

### 4. CopyOnWriteArrayList

定义：

CopyOnWriteArrayList 是 JUC 包下的线程安全版 ArrayList。

核心机制：

- 读不加锁。
- 写时复制。
- 写写互斥。
- 写完成后替换数组引用。

特点：

- 读写不互斥。
- 写写互斥。
- 写操作成本高，因为要全量复制。

适用场景：

- 读多写少。
- 数据量不大。
- 对实时一致性要求不极端。

## 五、线程池

记录日期：2026-04-08

### 1. 线程池价值

线程池是多线程运行工具。

核心价值：

- 降低线程频繁创建和销毁开销。
- 复用线程。
- 控制并发数。
- 通过阻塞队列削峰。
- 监控线程和任务状态。
- 提高任务响应速度。

### 2. 核心参数

- corePoolSize：核心线程数。
- maximumPoolSize：最大线程数。
- keepAliveTime：非核心线程空闲存活时间。
- unit：时间单位。
- workQueue：阻塞队列。
- threadFactory：线程工厂。
- rejectedExecutionHandler：拒绝策略。

### 3. 阻塞队列

- ArrayBlockingQueue：有界队列。
- LinkedBlockingQueue：默认无界队列。
- SynchronousQueue：不存储元素，直接移交。
- PriorityBlockingQueue：优先级队列。

### 4. 拒绝策略

- AbortPolicy：默认策略，直接抛异常。
- CallerRunsPolicy：由提交任务的线程执行任务。
- DiscardPolicy：直接丢弃任务，不抛异常。
- DiscardOldestPolicy：丢弃队头任务，尝试执行新任务。

### 5. 执行流程

1. 任务提交后，如果核心线程未满，创建核心线程执行。
2. 核心线程满了，任务进入阻塞队列。
3. 队列满了，创建非核心线程。
4. 线程数达到最大线程数后仍无法处理，触发拒绝策略。
5. 非核心线程空闲超过 keepAliveTime 后销毁。

### 6. 线程池线程为什么不会执行一次就结束

线程池工作线程内部使用循环不断从阻塞队列中获取任务：

```text
启动线程 -> run 方法循环 -> 从队列获取任务 -> 执行任务 -> 继续等待下一个任务
```

阻塞队列控制线程工作和休眠。

### 7. Executors 四类线程池

- SingleThreadExecutor：单线程，无界队列。
- FixedThreadPool：固定线程数，无界队列。
- CachedThreadPool：线程数可扩展，SynchronousQueue。
- ScheduledThreadPool：支持定时和延时任务。

注意：

- 面试中通常要说明不推荐直接使用 Executors，因为容易隐藏无界队列或无限线程数风险。

### 8. 线程池状态

- RUNNING：正常运行。
- SHUTDOWN：不接受新任务，但继续处理已有任务。
- STOP：不接受新任务，也尝试中断正在执行的任务。
- TIDYING：过渡状态。
- TERMINATED：终止状态。

### 9. 线程数设置经验

- CPU 密集型：CPU 核数 + 1。
- IO 密集型：CPU 核数 * 2。

实际项目中还应结合：

- 响应时间。
- 队列长度。
- 任务类型。
- 下游资源容量。
- 压测结果。

### 10. execute 与 submit

`execute`：

- 无返回值。
- 异常直接抛出。

`submit`：

- 返回 Future。
- 异常需要通过 `get()` 才能感知。

## 六、JVM

记录日期：2026-04-01、2026-04-09、2026-04-10

### 1. JVM 总体框架

JVM 是 Java 运行环境容器。

核心价值：

- 一次编译，到处运行。
- 自动内存管理。
- 垃圾回收。
- JIT 即时编译。

组成：

- 类加载子系统。
- 运行时数据区。
- 执行引擎。
- 本地方法接口。
- 垃圾回收器。

### 2. 类加载

定义：

类加载子系统将字节码文件转化为 JVM 内存中的 Class 对象。

核心价值：

- 让静态 class 文件变成运行时结构。
- 保证类唯一。
- 保护核心类不被篡改。
- 支持运行期动态加载。

阶段：

- 加载：读取二进制字节流，生成 Class 对象。
- 链接：
  - 验证：校验字节码合法性。
  - 准备：为静态变量赋零值。
  - 解析：符号引用转直接引用。
- 初始化：执行 `<clinit>`，完成静态变量赋值和静态代码块执行。

类加载器：

- 启动类加载器。
- 扩展类加载器。
- 应用类加载器。
- 自定义类加载器。

双亲委派：

- 自下往上委托父加载器。
- 父加载器找不到时，再自上往下尝试加载。

价值：

- 避免类重复加载。
- 防止核心类被篡改。

### 3. 运行时数据区

线程私有：

- 程序计数器。
- 虚拟机栈。
- 本地方法栈。

线程共享：

- 堆。
- 方法区 / 元空间。

程序计数器：

- 当前线程下一条字节码指令地址指示器。
- 线程私有。
- 唯一不会 OOM 的区域。
- 保证线程切换后能恢复执行位置。

虚拟机栈：

- 记录方法执行。
- 每个方法调用对应一个栈帧。
- 方法调用时栈帧入栈，方法返回时栈帧出栈。
- 可能出现 StackOverflowError 和 OOM。

栈帧组成：

- 局部变量表。
- 操作数栈。
- 动态链接。
- 返回地址。

本地方法栈：

- 记录 native 方法执行。
- 用于 JVM 与底层系统交互。

方法区 / 元空间：

- 存储类元数据、静态变量、常量等。
- JDK 8 后主要使用元空间。
- 线程共享。
- 可能 OOM。

堆：

- 存储对象实例和数组。
- GC 管理的主要区域。
- 线程共享。

堆结构：

- 年轻代：
  - Eden
  - Survivor0
  - Survivor1
- 老年代

年轻代：

- 管理朝生夕死的小对象。
- 适合复制算法。

老年代：

- 存放长期存活对象或大对象。
- 减少频繁 GC。

### 4. G1 垃圾回收器

定义：

G1 是面向服务端、低延时、分区、并发整理的垃圾回收器。

解决的问题：

- 大堆场景。
- 停顿不可控。
- Full GC 代价高。
- 内存碎片严重。

特点：

- 支持大堆。
- 可以设置最大停顿时间。
- 按 Region 分区。
- 垃圾优先回收。
- 并发标记。
- 复制整理，降低内存碎片。

面试表达：

> G1 通过把堆划分为多个 Region，优先回收垃圾收益高的区域，并结合并发标记和复制整理，在大堆场景下兼顾吞吐和低停顿。

## 七、设计模式

记录日期：2026-04-08、2026-04-09

### 1. 设计模式本质

核心理解：

> 在遵循单一职责的前提下，让调用方符合开闭原则。

单一职责：

- 对业务行为合理抽象。
- 避免大杂烩式万能方法。

开闭原则：

- 对修改关闭。
- 对扩展开放。
- 业务调用方尽量稳定。

### 2. 调用方理解

调用方不是创建对象的地方，而是真正执行业务的地方。

示例：

```java
// 创建对象的位置只是装配逻辑
if (type == ali) {
    pay = new AliPay();
}
if (type == wechat) {
    pay = new WechatPay();
}

// 真正调用方
pay.pay();
```

设计模式要保护的是：

- `pay.pay()` 这类业务调用入口。
- 让新增支付方式时，调用方少改或不改。

### 3. 项目中涉及的模式

AI 项目中提到：

- 策略模式。
- 模板方法模式。

适用方向：

- 优化重复代码。
- 抽象不同实现之间的变化点。
- 保持主流程稳定。

## 八、系统性能指标

记录日期：2026-03-25、2026-03-26

### 1. QPS 标准

记录中的经验区间：

- 慢：0-10。
- 正常：10-200。
- 快：300-1000。

### 2. EMA 平均响应时间

计算方式：

```text
平均响应时间 = 历史平均响应时间 * 0.9 + 当次响应时间 * 0.1
```

价值：

- 平滑瞬时波动。
- 反映近期响应趋势。
- 可用于限流和健康状态判断。

### 3. 数据库状态与连接池关系

类比：

- 连接池是数据库的办事窗口。
- 连接池活跃度是数据库的呼吸频率。
- 活跃度越高，数据库负载越大。

健康状态：

- 0-40%：空闲。
- 40%-70%：正常。
- 70%-85%：响应变慢、队列变长、业务卡顿。
- 大于 85%：阻塞、卡顿、CPU 飙升。
- 100%：数据库瘫痪。

可结合项目表达：

> 在元数据采集场景下，可以通过连接池活跃度、响应时间 EMA 和 QPS 判断数据库健康状态，再动态调整采集并发，避免采集任务拖垮数据库。
