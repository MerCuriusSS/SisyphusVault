### 2. 关键认知

记录中有一个非常重要的区分：

```text
业务循环查库 = 放大高成本 IO，业务数据庞大，严禁
元数据循环查库 = 极小成本系统表查询，官方标准，最优
```

这个区分很适合用于回答面试追问：

> 你为什么在元数据采集中允许循环查库？循环查库不是性能很差吗？

回答思路：

- 业务表循环查库确实会放大高成本 IO，因为业务表数据量大、查询复杂、容易影响线上性能。
- 但元数据采集查询的是系统表、表结构、字段、索引等元信息，数据量通常远小于业务数据。
- 各数据库官方本身也提供 information_schema 或系统 catalog 作为元数据查询入口。
- 所以元数据循环查询与业务数据循环查询不能简单等同。
- 真正需要控制的是采集频率、并发数和连接池压力。

### 3. SQL 方言适配

记录中提到“元数据采集 SQL 方言总结”，说明项目中可能涉及不同数据库的元数据查询差异。

## 三、项目亮点一：防 OOM 设计

记录日期：2026-03-27

### 1. 背景问题

元数据采集或大表比对场景中，如果一次性加载大量数据到内存，容易出现 OOM。

常见风险：

- 大表全量加载。
- 双大表嵌套比对。
- 查询结果一次性缓存。
- 对象集合持续膨胀。

### 2. 可包装方案

防 OOM 设计可以围绕以下方向表达：

- 分批查询。
- 流式处理。
- 避免一次性加载全量数据。
- 及时释放中间结果。
- 只保留必要字段或摘要。
- 对大对象做轻量化表示。

### 3. 简历表达

可写为：

> 针对元数据采集和大表比对过程中的内存膨胀风险，设计分批加载与摘要化比对方案，避免一次性加载全量数据导致 OOM，提升大数据量场景下的采集稳定性。

### 4. 面试表达

> 这个项目中一个风险是采集或比对的数据量不可控，如果直接把两边数据全部加载到内存，再做嵌套比较，很容易 OOM。所以我做了两个控制：第一是分批读取，控制单批数据量；第二是尽量只保留比对所需字段或 hash 摘要，避免保存完整大对象。这样内存占用从和全量数据强相关，变成和单批数据量强相关。

## 四、项目亮点二：双大表嵌套比对优化

记录日期：2026-03-27

### 1. 背景问题

双大表嵌套比对如果直接使用双层循环，复杂度会非常高。

典型问题：

```text
for each row in tableA:
    for each row in tableB:
        compare(rowA, rowB)
```

复杂度：

```text
O(N * M)
```

当两张表数据量较大时，性能不可接受。

### 2. 优化方向

记录中提到“hash 摘要快速比对设计”。

可推导为：

- 为关键字段或整行内容生成 hash 摘要。
- 使用 Map 建立摘要到数据的映射。
- 比对时通过 hash 快速判断是否一致。
- 将嵌套比对转化为近似线性比对。

### 3. 可包装方案

优化前：

- 双层循环。
- 复杂度 `O(N * M)`。
- 大表场景耗时严重。

优化后：

- 对一侧数据构建 hash 索引。
- 遍历另一侧数据时通过 hash 快速定位。
- 复杂度接近 `O(N + M)`。

### 4. 简历表达

可写为：

> 优化双大表嵌套比对逻辑，引入 hash 摘要快速比对方案，将原有双层遍历的高复杂度比较改造为基于摘要索引的快速匹配，显著降低大数据量比对耗时。

### 5. 面试表达

> 原方案如果对两张大表做双层循环比对，复杂度是 O(N*M)，数据量上来后基本不可接受。我把比对字段先标准化，然后生成 hash 摘要，并对其中一侧构建 Map 索引。另一侧遍历时直接根据摘要判断是否存在或是否一致，把比对过程从嵌套循环优化为接近 O(N+M)。

## 五、项目亮点三：Hash 摘要快速比对

记录日期：2026-03-27

### 1. 设计目的

Hash 摘要用于降低比对成本。

适用场景：

- 多字段比对。
- 大文本或大对象比对。
- 大表数据一致性校验。
- 元数据差异检测。

### 2. 核心思路

1. 选择参与比对的字段。
2. 对字段做标准化处理。
3. 拼接字段值。
4. 生成 hash 摘要。
5. 比对摘要而不是逐字段深度比较。

### 3. 注意事项

需要关注：

- 字段顺序必须稳定。
- 空值处理必须统一。
- 分隔符要避免歧义。
- hash 冲突虽然概率低，但严格一致性场景可能需要二次校验。

### 4. 可面试表达

> hash 摘要不是为了完全替代所有字段比较，而是作为快速过滤手段。大多数情况下摘要不同可以直接判定不一致；摘要相同时，如果业务要求强一致，可以再做一次字段级精确比较，这样兼顾性能和准确性。

## 六、项目亮点四：数据库元数据查询限流器

记录日期：2026-03-25、2026-03-26

### 1. 已记录内容

记录中提到：

- 限流器代码样例和理解。
- 数据库元数据查询限流器实现源码。
- EMA 计算平均响应时间。
- QPS 标准。
- 数据库状态与连接池关系。

### 2. 背景问题

元数据采集虽然查询的是系统表，成本比业务表低，但如果采集任务并发过高，仍可能造成：

- 数据库连接池被打满。
- 响应时间升高。
- 队列堆积。
- 业务查询受影响。

因此需要限流器保护数据库。

### 3. 指标设计

记录中涉及几个指标：

QPS 区间：

- 慢：0-10。
- 正常：10-200。
- 快：300-1000。

EMA 平均响应时间：

```text
平均响应时间 = 历史平均响应时间 * 0.9 + 当次响应时间 * 0.1
```

连接池活跃度：

- 连接池是数据库的办事窗口。
- 连接池活跃度是数据库的呼吸频率。
- 活跃度越高，数据库负载越大。

健康状态：

- 0-40%：空闲。
- 40%-70%：正常。
- 70%-85%：响应变慢、队列变长、业务卡顿。
- 大于 85%：阻塞、卡顿、CPU 飙升。
- 100%：数据库瘫痪。

### 4. 限流思路

可以将限流器描述为动态保护机制：

1. 采集任务发起元数据查询。
2. 限流器读取当前 QPS、平均响应时间、连接池活跃度。
3. 如果数据库健康状态良好，允许采集继续。
4. 如果响应变慢或连接池活跃度过高，降低采集并发。
5. 如果超过危险阈值，暂停或拒绝部分采集任务。

### 5. 简历表达

可写为：

> 设计数据库元数据查询限流器，基于连接池活跃度、QPS 和 EMA 平均响应时间动态判断数据库健康状态，在采集压力升高时主动降低并发，避免元数据采集任务抢占业务连接资源。

### 6. 面试表达

> 元数据采集虽然单次查询成本不高，但如果并发采集多个库或多个表，仍然可能把连接池打满。所以我设计了一个限流器，不只按固定 QPS 限制，而是结合连接池活跃度和响应时间趋势判断数据库状态。比如活跃连接超过 70% 后开始降速，超过 85% 后说明数据库已经有明显阻塞风险，就会进一步限制采集任务，避免影响业务查询。

## 八、项目亮点六：SQL 方言与元数据统一模型

记录日期：2026-03-25

### 1. 背景

不同数据库的元数据查询方式不同：

- 表信息查询不同。
- 字段信息查询不同。
- 索引信息查询不同。
- 注释、类型、约束的表达不同。

如果上层业务直接依赖各数据库 SQL，会导致逻辑分散、维护困难。

### 2. 优化方向

建议表达为：

- 针对不同数据库实现独立方言适配。
- 将查询结果转换成统一元数据模型。
- 上层流程只依赖统一模型。
- 新增数据库类型时，只扩展对应方言实现。

### 3. 简历表达

可写为：

> 抽象多数据库元数据采集模型，针对不同 SQL 方言实现表、字段、索引等元信息查询适配，将异构数据库元数据统一映射为标准模型，降低上层采集流程对具体数据库的耦合。

可以按 2 分钟版本准备：

## 十二、推荐面试回答：最大难点

> 这个项目的难点不是单条元数据 SQL 怎么写，而是采集规模上来之后如何保证稳定性。比如多库多表同时采集时，虽然查的是系统表，但并发过高仍然会打满连接池；大表比对时，如果直接全量加载和双层循环，也会带来 OOM 和性能问题。所以我主要从两个方向处理：一是用分批和 hash 摘要降低比对成本，二是用连接池活跃度、QPS 和响应时间做动态限流，控制采集任务对数据库的压力。

## 十三、推荐面试回答：为什么这是项目亮点

> 这个亮点主要在于它不是简单写 CRUD，而是围绕真实数据场景做稳定性和性能优化。元数据采集本身看起来只是查询系统表，但放到多数据源、多表和高并发采集场景下，就会遇到连接池压力、响应时间抖动、OOM、大表比对慢等问题。我的方案把采集流程、比对算法和数据库保护机制结合起来，既保证了采集效率，也降低了对业务数据库的影响。
