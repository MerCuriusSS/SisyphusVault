## 四、SSE 流式输出

记录日期：2026-04-09

### 1. 使用场景

应用与大模型对话时，模型生成内容不是一次性返回，而是逐段生成。SSE 适合这种服务端持续向前端推送文本片段的场景。

### 2. 已发现问题

问题一：前端接收内容会丢失空格。

解决方式：

- 使用 JSON 格式对数据进行上层封装。
- 避免纯文本片段在传输或解析时丢失格式信息。

问题二：前端默认无法判断 SSE 是否结束。

解决方式：

- 正常输出结束后追加结束事件。
- 结束事件携带空数据或明确结束标识。

### 3. 项目亮点表达

可面试表达：

> 在大模型流式输出场景中，最开始直接传输文本片段会出现前端空格丢失的问题，我将输出内容统一封装为 JSON 事件，保证格式不被解析过程破坏。同时补充结束事件，让前端能明确区分正常结束、异常中断和仍在生成三种状态。

可追问方向：

- 为什么不用普通 HTTP 一次性返回？
- SSE 和 WebSocket 有什么区别？
- 如何处理模型生成异常？
- 如何处理前端刷新或断连？
- 如何标识一次对话的完整生命周期？

### 2. 本地预览机制

接口格式：

```text
http://localhost:8123/api/static/{deployKey}[/{fileName}]
```

处理逻辑：

- 从访问路径中截取文件名称。
- 路径格式为 `/{deployKey}[/{fileName}]`。
- 将路径与本地部署目录拼接。
- 查找文件并返回文件内容。

### 3. Nginx 匹配规则

记录中的 Nginx 配置：

```nginx
location ~ ^/([^/]+)/(.*)$ {
    try_files /$1/$2 /$1/index.html =404;
}
```

匹配逻辑：

1. 优先查找目标目录下的对应文件。
2. 如果对应文件不存在，则返回目标目录下的 `index.html`。
3. 如果仍不存在，则返回 404。

项目意义：

- 支持部署后的应用直接访问。
- 支持前端单页应用路由回退到 `index.html`。
- `deployKey` 可用于隔离不同用户或不同应用的部署目录。

可面试表达：

> 应用部署后，我通过 deployKey 将不同应用隔离到独立静态目录。访问时先根据 URL 解析 deployKey 和文件路径，优先返回实际文件；如果是前端路由，则回退到该应用目录下的 index.html，从而支持 SPA 应用刷新和子路由访问。

## 六、对话历史模块

记录日期：2026-04-14、2026-04-16

### 1. 模块背景

AI 对话需要保存用户与模型之间的历史消息，支持用户查看历史对话，并为后续上下文记忆提供数据基础。

### 2. 分页方案选择

传统分页：

定义：

- 指定页数和每页条数。

示例：

```sql
select * from user limit 1, 5;
```

优点：

- 简单。
- 支持跳页。
- 适合常规管理后台。

缺点：

- 数据频繁增删时，可能出现重复显示或遗漏。
- 大偏移量查询性能较差。

游标分页：

定义：

- 从上次结束位置继续查询。

示例：

```sql
select * from user where user_id > 5 limit 5;
```

优点：

- 适合增量加载。
- 适合数据频繁变化场景。
- 大数据量下查询更稳定。

缺点：

- 不支持任意跳页。

适用场景：

- 即时通讯。
- 推送数据流。
- AI 对话历史。
- 下拉滚动翻页。

### 3. 当前项目选择

AI 对话历史采用游标分页更合适。

原因：

- 对话记录按时间递增。
- 用户通常是下拉或上滑加载更多。
- 不需要强跳页。
- 数据可能持续新增。
- 游标分页更适合大数据量和实时数据流。

可面试表达：

> 对话历史模块我没有使用传统页码分页，而是选择游标分页。因为聊天记录天然是时间流，用户通常按最新消息向前翻，不需要任意跳页；同时游标分页可以避免数据新增导致的重复或遗漏问题，也能降低大偏移量查询带来的性能损耗。

## 七、上下文记忆模块

记录日期：2026-04-15、2026-04-16

### 1. 问题背景

当前 AI 对话框没有上下文记忆。

影响：

- 模型无法理解历史对话。
- 多轮对话割裂。
- 用户体验较差。
- 无法支持复杂任务的持续生成和修改。

### 2. 解决方案

开启上下文记忆模块：

- `chatMemory`

存储介质选择：

- Redis：临时存储，响应快。
- MySQL：持久化存储，不丢失。

分页查询：

- 使用游标查询代替传统分页。
- 按最新时间进行下拉滚动翻页。

### 3. Redis 与 MySQL 分工

Redis：

- 保存短期上下文。
- 读写快。
- 适合在线对话时频繁读取。
- 可设置过期时间。

MySQL：

- 保存完整历史。
- 支持持久化。
- 支持用户历史记录查询。
- 支持后续数据分析和审计。

推荐架构表达：

> 在线对话时优先从 Redis 读取最近上下文，保证响应速度；完整消息异步或同步写入 MySQL，保证历史记录不丢失。历史查询走 MySQL 游标分页，模型上下文则根据 token 限制从 Redis 或 MySQL 中截取最近消息。

### 4. 后续可扩展点

可继续补充：

- 长对话摘要压缩。
- 基于 token 数量裁剪上下文。
- 用户级、应用级、会话级记忆隔离。
- 系统提示词与用户历史消息分层管理。
- 对话记忆过期策略。

## 十一、建议沉淀的面试故事

### 故事一：为什么使用 SSE

回答结构：

1. 大模型输出是逐段生成，一次性返回体验差。
2. SSE 适合服务端向客户端持续推送文本。
3. 项目中遇到空格丢失和结束状态不明确问题。
4. 通过 JSON 封装和结束事件解决。

### 故事二：为什么对话历史使用游标分页

回答结构：

1. 聊天记录是时间流。
2. 用户通常滚动加载，不需要跳页。
3. 传统分页在数据新增时容易重复或遗漏。
4. 游标分页性能更稳定。

### 故事三：如何设计上下文记忆

回答结构：

1. 无记忆会导致多轮对话割裂。
2. Redis 保存短期上下文，提升读取速度。
3. MySQL 保存完整历史，保证不丢失。
4. 后续可结合 token 裁剪和摘要压缩。

### 故事四：如何实现应用部署和预览

回答结构：

1. 每个应用通过 deployKey 隔离目录。
2. 后端根据 URL 定位静态文件。
3. Nginx 优先匹配真实文件。
4. 前端路由回退到 index.html。

### 故事五：为什么升级为工程化前端生成

回答结构：

1. 单文件 HTML 只能覆盖简单页面。
2. 真实项目需要组件化、依赖管理和构建。
3. 升级为 Vite + Vue3 工程结构。
4. 生成结果更接近可维护、可部署项目。
