### Q2：NAS 落盘系统中，如何解决高吞吐量下的数据一致性问题？

```
1.位于消费端，采用“at-least-once”语义，即写入数据，再手动ack
2.实现上设计跨线程ackQueue回传机制，每个消费者分配一个ackQueue阻塞队列，拉取的消息持有引用，当消息成功写入文件后，按照topic_分区的分组合并最大偏移量，塞入ackQueue队列，最后提交到消费者完成手动提交。
```

### Q4：多消费者并行拉取消费时如何防止数据冲突？批量写入时又是如何确保数据完整性和一致性？
```
防数据冲突机制：
1.分区隔离，同消费组，kafka保证一个分区只能被一个消费者消费。
2.阻塞队列保证线程安全
3.单writer写入，无锁竞争。

完整性：
数据按批次处理，且以完整行落盘。

一致性：
批数据flush()成功后才通过ackQueue提交偏移量。

```

### Q5：如何解决高并发情况下，多个消费者同时提交消费位点可能出现的冲突？

```
同分区消费位点重复提交？
1.kafka的分区隔离保证一个分区只有一个消费者提交

同分区消费点覆盖？
2.提交前先按分区-消费点最大值合并，一分区只对应一消费点。

```

### Q6：如何通过流式采集链路和EMA限流保障系统稳定性？EMA在当中的作用？

```
流式采集链路：
1.原来一次性拉取全部元数据加载内存，大库容易 OOM；现在通过游标分页进行分批，处理一批落库一批释放内存，避免全量对象驻留堆内。

2.EMA就是指数移动平均，通过为波动数据和大样本数据分配不同权重以降低毛刺影响，在项目中主要用于计算平均响应时间，按照平均响应时间、最后一次响应时间的8:2比重，过滤掉偶发慢查询带来的毛刺，避免误降级。
```

### Q8：如何在限流后恢复系统的正常运行？

```
项目采用的是三合一健康判断，当连接池使用率、错误率、平均响应时间全部低于阈值时接触限流限制（使用率<0.8,错误率<5%,平均响应时间<500ms）
```

### Q9：项目中有遇到OOM问题吗？请描述定位并解决OOM过程中，使用了哪些工具？如何分析堆内存分布？

```
1.解决库表采集过程中遇到OOM问题
2.工具：jmap和MAT；jmap下载dump文件；MAT分析OOM原因；
3.过程：
1）根据日志得知OOM问题
2）获取jmap生成的dump文件
3）在MAT中打开，通过leak-suspect 快速定位疑似泄露
4）从dominator-tree中按retained-heap排序，看到内存占比非常大的arrayList，里面保存大量表、字段等元数据对象。
5）得出是全量采集库表数据引起的OOM结论，遂定位业务代码并修复

```
