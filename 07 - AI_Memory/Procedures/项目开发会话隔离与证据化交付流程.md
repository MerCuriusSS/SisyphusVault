# 项目开发会话隔离与证据化交付流程

## Context

在开发项目时，需求讨论、方案决策、写代码、跑测试、查看日志和反复返工如果全部塞进同一个会话，容易造成上下文混杂：当前阶段不清楚，决策依据难以追踪，执行结果和需求目标相互污染，返工时也很难准确回滚到某个已知状态。这个问题的核心不是会话数量本身，而是没有把思考、执行、验证和归档划分为可追踪的边界。

这套方法的目标是让需求在主线程中被充分想清楚，让代码由执行分身按确认后的规格完成，让每次交付都携带可核验的证据，并让错误保留在可回滚的 Git 历史中。它适合作为个人项目或 Agent 协作项目的默认开发流程；目前属于个人总结形成的 draft，后续应在实际项目中验证并修订。

## 反模式与基本原则

不要把需求澄清、方案拍板、编码实现、测试排错和返工混成一个没有阶段边界的长会话。主线程负责保持问题背景、需求范围、方案决策和验收标准的一致性；执行分身负责在明确约束下修改代码、运行测试和完成 Review。分工的目的不是增加流程，而是让每个阶段都有清晰的输入、输出和责任边界。

每次改动都必须可追踪、可回滚、可验证。项目初次创建时，先创建本地 Git 仓库，并在 AGENTS.md、CLAUDE.md 等 Agent 指令文件中写入项目级规范：每次改动完成后创建对应的 Git commit；每次改动后编写或更新相关测试；交付用户前确保所有测试和验证全部通过。若项目尚未具备测试基础设施，应先记录这一缺口，并把补齐最小可执行验证作为交付前置条件，而不是把“暂时没有测试”当成通过。

## 标准流程

1. 需求炼化：使用 Grill 把模糊需求拆成目标、用户场景、范围、非目标、约束、风险和验收条件。对于仍然存在的歧义，要保留为待确认问题，不能直接让执行分身猜测。
2. 规格确认：使用 Spec 把炼化后的结果固化为双方确认的规格。当范围、接口、行为、边界和验收标准已经确认时，明确标记为 SPEC READY。没有达到 SPEC READY 的内容，不进入正式编码阶段。
3. 主线程派工：主线程保留需求和方案上下文，Fork 一个执行分身。分身接收 SPEC、相关项目文件、限制条件、测试要求和验收命令，只在授权范围内写代码。
4. 分身执行：分身完成实现，同时编写或更新相关测试，运行测试和必要的静态检查、构建、集成验证或手工验收，并完成一次 Review。实现、测试和验证应形成同一组可追踪改动。
5. Receipt 回传：分身完成后自动向主线程返回 Receipt。Receipt 至少说明完成了什么、修改了哪些文件、使用了哪个 commit、运行了哪些测试或验证命令、结果是什么、是否存在已知风险或未完成项。主线程依据 Receipt 和证据验收，而不是只依据“已完成”的口头结论。
6. 问题闭环：如果测试、Review、Receipt 或验收发现问题，主线程将具体问题和复现证据打回同一个执行分身重修。重修仍需更新测试、重新验证并产生新的 commit 和 Receipt。只有验收条件全部满足后，才允许自动归档本次工作。
7. 大任务扩展：当任务规模超过一个分身或一个工作目录的合理承载范围时，先创建 Goal，再按边界拆成多个 Worktree 和相互独立的工作包，使用不同模型或执行分身并行推进。每个并行分支都必须有清晰输入、独立 commit、测试证据和 Receipt；主线程负责合并前的冲突处理、整体验收和最终归档。

## 输入、输出与验收门槛

每个开发单元至少应具备以下状态流转：

`需求草稿 -> Grill 炼化 -> Spec -> SPEC READY -> Fork 执行 -> 测试与 Review -> Receipt -> 主线程验收 -> 归档`

对应的硬门槛是：

- 没有清晰范围和验收条件，不派发编码。
- 没有 SPEC READY，不进入正式实现。
- 没有相关测试或验证，不视为完成。
- 没有 Git commit，不视为可交付。
- 没有 Receipt 和可复核证据，不进入主线程验收。
- 测试失败、Review 有问题或验收不通过，自动回到执行阶段重修。
- 只有所有测试和验证通过，且已知风险被记录或接受，才归档。

## Receipt 建议格式

Receipt 可以使用固定结构，便于主线程快速判断：

- Scope: 本次实现覆盖的需求和未覆盖范围
- Changes: 修改文件、关键行为和配置变化
- Commit: commit hash 和提交说明
- Tests: 测试/构建/静态检查/手工验证命令及结果
- Review: Review 发现、已修复问题和剩余风险
- Acceptance: 对照 SPEC READY 验收条件的逐项结论
- Follow-up: 必须后续处理的事项；没有则明确写无

## 适用边界与演进

小型、一次性的探索可以暂时使用轻量流程，但一旦代码会保留、需要多人或 Agent 协作、存在外部依赖，或修改可能影响已有行为，就应至少保留本地仓库、指令文件、测试、commit 和验证记录。分身、Worktree、不同模型和自动归档是随任务规模增长的扩展，不应为了形式给每个微小改动增加不必要的并行开销。

这套方法解决的是协作边界和证据链问题，不替代产品决策、代码 Review、持续集成或发布审批。Git commit 只能提供版本回滚能力，不能证明实现正确；测试通过也不能替代对 SPEC READY 和业务验收条件的核对。
