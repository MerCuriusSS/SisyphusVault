```
L1:
如何保证 MQ场景下，业务数据、消息投递、消息消费的最终一致性

L2：
生产者阶段，业务结果消息可追踪、异常场景可补偿
Broker阶段，消息必须可靠存储、刷盘、复制
消费者阶段，必须业务成功后再确认消息
重复投递时，业务结果不能重复消费
有顺序要求时，同一业务对象的消息不能乱序
异常时，系统必须能补偿、告警、对账

L3：
生产者阶段 -> 发送确认+失败重试/事务消息/本地消息表
broker阶段 -> 消息持久化+同步刷盘+主从复制
消费者阶段 -> 手动 ACK，失败重试，超过阈值进入死信队列
重复投递不重复生效 -> 唯一id去重+状态机幂等+消费记录表
同一业务对象消息不乱序 -> 生产者按业务 key 路由到同一队列/分区，消费者局部串行处理
异常可补偿 -> 补偿任务+监控告警+业务对账

L4：
失败日志+定时补偿
├─ 流程：本地事务提交 -> 写 MQ -> 失败后记日志 -> 定时任务重发

MQ 事务消息
├─ 流程：发送半消息 -> 执行本地事务 -> commit / rollback 半消息
├─ 成功：提交半消息，消费者可消费
├─ 回滚：删除半消息
├─ 中断：Broker 回查本地事务状态

本地消息表 Outbox
├─ 流程：写业务表 + 写 outbox_message 在同一个数据库事务中完成
├─ 提交后：后台任务扫描 PENDING 消息并投递 MQ
├─ 成功：状态改为 SENT
├─ 失败：增加 retry_count，更新 next_retry_time，等待下次重试

Broker 可靠存储：消息落盘，避免 Broker 重启丢消息

消费者手动 ACK：先处理业务，后 ACK；手动 ACK 解决“不轻易丢”，但会带来“可能重复”

消费端幂等：消息可以重复投递，但业务结果只能生效一次
├─ 唯一业务id
├─ 状态机幂等
├─ 唯一消息记录表

消息顺序性
生产者：同一id分送到同一队列/分区
消费者：单线程消费/按业务key串行处理

L5：
订单创建成功后必须发送订单创建消息
支付成功消息重复投递
消费者业务处理成功但 ACK 失败
Broker 宕机后核心消息不能丢
同一订单状态消息乱序
```
