[「记忆规律」与「知识体系建设」](「记忆规律」与「知识体系建设」.md)

```
L1：核心问题
如何保证 Redis 和 DB 的双写最终一致性，并降低线上脏读风险？

L2：方案
├─ 确认缓存模式：
├─ 选择正确写路径：
├─ “先删除缓存后再回填旧值”极端时序下脏数据的有效性处理&删除可靠性
├─ 处理缓存保护问题
├─ 多级缓存一致性
├─ 按业务等级选方案

L3：机制
├─ 确认缓存模式：旁路缓存
├─ 选择正确写路径：先更新DB，再删除缓存
├─ “先删除缓存后再回填旧值”极端时序下脏数据的有效性处理延迟双删 / MQ异步删除补偿 / 
├─ 删除可靠性：同步重试 / MQ可靠性 / TTL兜底
├─ 缓存保护：参数校验 / 空值缓存 / 布隆过滤器 /  分布式锁 / 逻辑过期 / TTL随机值 / 限流降级 / 高可用
├─ 多级缓存一致性：本地短 TTL / redis发布订阅 / MQ广播 
├─ 方案选择依据：并发度、可靠性与解耦、多渠道&业务代码依赖性

L4：机制细节
├─ 旁路缓存：
	DB作为事实数据源
	读：缓存->DB->更新缓存
	写：更新DB->删除缓存
├─ 正确写路径：
	【先删后改】问题：线程A先删除缓存，线程B查询DB并回填旧值后，线程A再更新DB
	【先改后删】问题：线程A先完成查询DB，线程B更新DB并删除缓存后，线程A再回填旧值
├─ 处理极端时序：
	延迟双删：删除缓存后，延迟若干时间后再删一次缓存
	MQ异步删除补偿：更新 DB -> 缓存删除->延迟发送缓存失效消息 -> 消费者删除缓存
├─ 删除可靠性：
	同步重试：删除失败后立即重试几次
	MQ可靠性：本地消息表+MQ持久化+手动ACK
	TTL兜底：最终兜底方案，避免删除失败后无限期脏读
├─ 缓存保护：
	├─ 缓存穿透：
		原因：查询不存在的数据，每次都打DB
		机制：参数校验、缓存空值、布隆过滤器、限流风控
	├─ 缓存击穿：
		原因：单个热点 key过期，大量请求同时查DB
		机制：分布式锁重建缓存，或逻辑过期 + 后台异步刷新
	├─ 缓存雪崩：
		原因：大量 Key 同时过期，或 Redis 整体不可用
		机制：TTL 加随机值、Redis 高可用、熔断降级
├─ 多级缓存一致性：
	机制：Caffeine + Redis 多级缓存
	场景：
		单应用：本地短 TTL兜底
		多应用：Redis 发布订阅模型
		多应用+可靠性：MQ可靠广播
	
L5：应用场景
1. 更新商品价格后，Redis 删除失败，用户一直看到旧价格，你怎么补偿？
2. A 请求查 DB 旧值准备回填，B 请求更新 DB 并删除缓存，A 最后回填旧值，怎么处理？
3. 后台脚本直接改了库存，业务应用不知道，Redis 仍是旧值，怎么设计？
4. Caffeine + Redis 场景，Redis 已删，但某台机器仍返回旧值，问题在哪？
5. 热点商品 Key 过期瞬间 DB QPS 飙升，这是穿透、击穿还是雪崩？
6. Redis Pub/Sub 和 MQ 都能通知本地缓存失效，什么时候选 MQ？
```
