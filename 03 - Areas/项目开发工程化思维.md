### 🟣 核心价值：拒绝“凭感觉、凭记性”，让项目“有目标、有图纸、有步骤、可控制”。

## ⚡️ 我的重构
>它的底层逻辑是什么？（尝试用最简单的类比解释给外行听）它的结构是什么?

### 🟣 底层逻辑：用流程和方法，将项目由”模糊“到”明确“、由”复杂“拆解成”简单“、由”不可控“到”可控“、由”变化“转化为”可重复迭代“。

### 🟣 组成部分：

#### 一、**需求分析和规划：确定方向**

1. 产出物：需求文档（prd）
2. 面向对象：**业务人员**
3. 价值：回答做什么、为什么做（**what、why**）
4. 文档内容：
	- **业务背景与现状**：当前存在什么问题？为什么要做这个功能？
	- **业务目标**：要达成什么目的？哪些做、哪些**不做**？
	- **目标用户 / 使用角色**
	- **业务功能清单**：业务视角功能点（业务语言、非技术接口、字段）
	- **业务流程**：主流程/次流程（业务语言）
	- **风险、依赖、假设条件**：依赖外部系统、第三方；业务风险；前提假设
	- **周期、优先级**：P0必做；P1、P2后续迭代；排期


#### 二、**详细设计：具体文档**

1. 产出物：架构文档、库表设计、接口文档、测试报告、运维方案等
2. 面向对象：后端、前端、测试技术人员
3. 价值：回答在「技术层面」如何实现（**How**）
4. 文档内容：
	- **整体系统架构**：架构图、模块划分、服务依赖关系
	- **技术流程**：业务流程翻译成技术流转逻辑，系统之间如何交互
	- **数据流转**：哪些字段、从哪里来、到哪里去、如何变化
	- **数据库表设计**：表结构、字段、索引、关联关系、数据字典
	- **接口设计**：入参、出参、请求方式；正常场景返回
	- **异常处理策略**：报错场景、降级、重试、缓存策略
	- **安全、性能方案**：限控制、并发、限流、数据脱敏

##### 业务流程、技术流程、数据流转的区分

业务流程：强调业务规则（**人话**）
```
1. 用户选择商品，提交下单
2. 校验库存是否充足
3. 库存充足：生成订单；库存不足：返回下单失败
4. 生成订单后扣减商品库存
5. 创建待支付订单，等待用户付款
6. 如果 30 分钟没付款，自动取消订单，归还库存
```

技术流程：强调「**系统内**」执行逻辑、模块调用、异常、分支

```
用户请求→订单服务接收下单请求
① 参数校验：检查入参（用户ID、商品ID、购买数量是否合法）
② 调用库存服务【查询库存接口】，传入商品ID、购买数量
    分支A：库存服务返回库存不足 → 返回错误码，结束本次下单，返回前端“库存不足”
    分支B：库存充足，继续往下走
③ 开启数据库事务
    3‑1 订单服务调用订单DAO，向订单表插入一条待支付订单记录
    3‑2 RPC调用库存服务【扣减库存接口】，执行库存扣减
    3‑3 如果扣库存失败，触发事务回滚，返回下单失败
④ 事务提交，订单创建成功
⑤ 发送延迟消息(MQ)：30分钟后触发订单超时任务
⑥ 返回成功响应给前端
【异步任务】：延迟消息到期后，执行超时逻辑
    1）查询订单状态，判断是否还是【待支付】
    2）如果是待支付：调用库存服务执行库存回补；更新订单状态为已取消
    3）如果订单已经支付，直接忽略该任务，不做任何操作
```

数据流转：强调用到哪些字段、从哪里来、到哪里去，字段怎么变

```
1. 前端传入数据：`{userId, goodsId, buyNum}` → 网络传输到订单服务
2. 订单服务把`goodsId,buyNum`传给库存服务；库存读取库存表`goods_stock`的 stock 字段
3. 订单服务生成订单数据：orderId、userId、goodsId、orderStatus = 待支付，写入数据库`order`表
4. 库存服务修改`goods_stock`表中 stock = stock‑buyNum
5. MQ 消息携带：orderId、超时时间，投递到消息队列
6. 超时任务读取 order 表，若未支付：修改 orderStatus = 取消；库存服务更新 goods_stock，库存 + buyNum
```
