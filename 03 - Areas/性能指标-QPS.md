## 💥 核心结论
>核心定义是什么? 核心价值在哪里?

### 🟣 核心定义：每秒请求数量（query per second）

### 🟣 核心价值：衡量一个系统的压力/流量大小，非性能分数

## 🔪 我的见解
>为什么要记录它「我遇到了什么问题」？它能解决哪些痛点？

### 🟣 遇到哪些问题？
- 不清楚系统承受的压力/流量标准
- 不清楚使用限流器限流时的用量是多少？
- 如何估算一个系统的QPS？

### 🟣计算公式：
QPS上限=`有限并发线程数/单次请求平均耗时（RT）`


### 🟣压测估算法则
- 错误率（**核心**）：<5%，决定系统**能不能活**
- RT：不同场景要求不一样，决定系统有没有排队（高并发系统【C端】：<300ms；内部系统：<1s~5s不等）
**RT常规标准**

| 接口类型    | 业务场景         | 常规RT     |
| ------- | ------------ | -------- |
| 内存接口    | 本地查内存、枚举、无IO | <10ms    |
| redis查询 | 普通get/set    | <20ms    |
| 数据库单表查询 | 主键、唯一索引      | <50ms    |
| 数据库单表查询 | 普通索引         | <100ms   |
| 数据库多表关联 | 连表、子查询、排序    | <300ms   |
| 第三方接口   | 外部HTTP接口、支付  | <1s      |
| 复杂业务计算  | 大数据量封装、循环逻辑  | 500ms-2s |

- CPU

### 🟣与TPS的比较
- 定义：每秒完成的业务数量【1TPS 即用户完成一次完整业务操作所调用的接口集合（1TPS=nQPS）】
- TPS的测量：
	1. 把一次完整业务操作所需的接口做成事务脚本
	2. 持续加压测试（线程数量&测试时间）
	3. 一次业务操作全部成功算1TPS
	4. TPS=成功操作/时间

## ⛪ 场景设想（瓶颈推测）
- CPU随QPS上升而暴涨（QPS⬆️ CPU⬆️）：CPU计算量大，瓶颈在CPU
- RT随QPS上升而暴涨（QPS⬆️ RT⬆️）：请求在排队，瓶颈在数据库（慢查询）、外部接口（响应慢）
- 错误率随QPS上升而暴涨（QPS⬆️ 错误率⬆️）：瓶颈在连接池（连接池不够、超时时间短）
