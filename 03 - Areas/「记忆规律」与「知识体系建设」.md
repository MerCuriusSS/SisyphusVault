## 人为什么反复遗忘「死板的知识概念」？

- 人类的记忆规律擅长 「记忆锚点->建立关系->形成结构->提取加固」发散结构。
- 记忆锚点的选取需要有发散意义，如「问题驱动、因果链」，而非「孤立定义、平铺分类、缺乏场景的术语」


## 拆解与建设

- 「5W1H」适合认知事物，强调拆解过程，但其孤立的概念定义对记忆有负担。
- 「问题锚点」适合构建体系，强调由问题发散开，将各个孤立的知识建立关系。

## 「知识体系建设记忆模型」建设

### 体系建立

```
L1：核心问题
L2：关键原因
L3：解决机制
L4：机制细节
L5：应用场景、验证和优化
```

### 单点深入

```
1.【选取问题锚点】
描述这个东西用来解决什么问题？

2.【背景原因】
为什么会出现这个问题？

3.【解决方案】
1）什么方式解决？
2）作为主线继续按照“问题 -> 原因 -> 方案 -> 原理 -> 代价 -> 验证 -> 场景”进行新一轮展开；

4.【底层原理】
具体怎么实现？

5.【使用场景】
什么时候适合用？

6.【风险】
有哪些限制/边界条件

7.【验证方式】（如果需要）
如何判断有没有效？

8.【优化】（如果需要）
如果效果不好，怎么优化？
```


## 实践示例-SQL调优

### 体系建立

#### L1 核心问题
```
一条 SQL 为什么慢？
```

#### L2 关键原因
```
扫描太多
回表太多
排序太重
临时表太大
返回太多
锁等待太久
```

#### L3 解决方案/机制
```
扫描太多 -> 索引、B+ 树、最左前缀
回表太多 -> 聚簇索引、二级索引、覆盖索引、ICP
排序太重 -> 联合索引匹配 order by，避免 filesort
临时表太大 -> 优化 group by、减少中间结果
返回太多 -> limit、分页、只查必要字段
锁等待太久 -> 缩短事务、合理索引、MVCC、行锁
```

#### L4 机制细节
```
索引
├── B+ 树
│   ├── IO 少
│   ├── 范围快
│   └── 性能稳
├── 聚簇索引
├── 二级索引
├── 回表
├── 覆盖索引
├── 联合索引
├── 最左前缀
└── 索引下推
```


#### L5 验证优化
```
Explain
├── type：访问类型
├── key：实际使用索引
├── rows：预估扫描行数
└── Extra：Using index、Using filesort、Using temporary
```
### 单点深入-覆盖索引

#### 1.锚点问题
```
二级索引查询为什么走了索引还可能慢？
```

#### 2.背景原因
```
InnoDB 的二级索引叶子节点只保存索引列和主键值，不保存完整行数据。
如果查询字段不在二级索引中，就要通过主键再去聚簇索引查询完整行，这就是回表。
大量回表会带来随机 IO。
```

#### 3.核心机制/解决方案
```
覆盖索引让查询所需字段都能从索引中直接获取，不需要回表。
```

#### 4.底层原理
```
如果 select 字段、where 条件字段、order by 字段都包含在同一个联合索引中，
MySQL 可以直接扫描索引并返回结果，不需要再访问聚簇索引中的完整行数据。
```

#### 5.使用场景
```
高频查询
返回字段较少
二级索引过滤后结果较多
需要减少回表
order by 可以和索引顺序结合
```

#### 6.代价风险
```
索引字段越多，占用空间越大。
写入、更新、删除时维护成本更高。
联合索引过宽会降低写性能，也可能影响 buffer pool 利用率。
```

#### 7.验证方式（如果需要）
```
Explain 的 Extra 出现 Using index，通常说明使用了覆盖索引。
同时关注 type、key、rows，确认扫描范围是否合理。
```


#### 8.优化方向（如果需要）
```
避免 select *
只查询必要字段
根据 where + order by + select 设计联合索引
不要为了覆盖索引盲目把大量字段塞进索引
```
